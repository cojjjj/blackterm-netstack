# BLACKTERM // NETSTACK

> A userspace IPv4 networking stack written from scratch in C.

BLACKTERM NETSTACK is an experimental networking stack that constructs, serializes, parses, transmits, and receives network protocols directly from userspace on Linux.

Instead of relying on the operating system's TCP/IP stack for transport behavior, NETSTACK implements the protocol logic itself and communicates with the network through raw Ethernet frames.

The project currently implements a working path from:

```text
HTTP
  ↓
TCP
  ↓
IPv4
  ↓
Ethernet
  ↓
Linux AF_PACKET
  ↓
NIC
```

It can perform ARP resolution, send ICMP Echo Requests, issue DNS queries over UDP, establish TCP connections using a custom TCP state engine, and retrieve HTTP pages using packets generated by the stack.

---

## Current Status

BLACKTERM NETSTACK currently supports:

- Ethernet II frame construction and parsing
- ARP request/reply handling
- IPv4 packet construction and parsing
- IPv4 header checksum calculation and validation
- ICMP Echo Request and Echo Reply
- UDP datagrams and IPv4 pseudo-header checksums
- DNS A queries and response parsing
- DNS compression pointers
- TCP segment construction and parsing
- TCP IPv4 pseudo-header checksums
- TCP connection state tracking
- TCP sequence and acknowledgment tracking
- TCP retransmission timers
- TCP exponential backoff
- TCP FIN and RST handling
- HTTP/1.1 GET requests
- HTTP response parsing
- HTTP chunked transfer decoding
- Raw packet transmission through Linux `AF_PACKET`
- Direct-subnet and default-gateway routing
- Live ARP → TCP → HTTP communication

The stack has been tested against real network hosts rather than only synthetic packet fixtures.

## Protocol Stack

### Ethernet

NETSTACK can construct, serialize, parse, and validate Ethernet II frames.

```text
+-------------------+
| Destination MAC   |
+-------------------+
| Source MAC        |
+-------------------+
| EtherType         |
+-------------------+
| Payload           |
+-------------------+
```

Supported EtherTypes currently include:

```text
0x0800  IPv4
0x0806  ARP
```

---

### ARP

ARP is used to resolve IPv4 addresses into Ethernet MAC addresses before packets are transmitted.

Example:

```text
ARP  who-has 192.168.50.1
ARP  192.168.50.1 is-at C8:7F:54:C1:A1:20
```

For remote destinations, NETSTACK resolves the default gateway rather than attempting to ARP for the remote host.

---

### IPv4

The IPv4 implementation includes:

- packet construction
- serialization
- parsing
- address formatting
- protocol identification
- checksum generation
- checksum validation
- malformed packet rejection

IPv4 packets can carry:

```text
ICMP
UDP
TCP
```

---

### ICMP

NETSTACK implements ICMP Echo Requests and Replies.

That allows the stack to perform its own ping operation without using the system `ping` implementation.

Example:

```text
BLACKTERM // NETSTACK

interface: eno1
local IPv4: 192.168.50.62
target: 8.8.8.8
route: via 192.168.50.1

ARP  who-has 192.168.50.1
ARP  192.168.50.1 is-at C8:7F:54:C1:A1:20

ICMP echo request id=0x4242 seq=1
ICMP echo reply from 8.8.8.8 ttl=250 seq=1 time=39.90 ms
```

---

### UDP

UDP support includes:

- datagram construction
- serialization
- parsing
- IPv4 pseudo-header checksums
- checksum verification
- corruption detection
- malformed packet rejection

UDP provides the transport layer currently used by the DNS implementation.

---

### DNS

NETSTACK can generate DNS queries and parse DNS responses directly over its UDP/IPv4/Ethernet stack.

Implemented features include:

- A queries
- DNS wire-format encoding
- response parsing
- compression pointers
- IPv4 record extraction
- TTL parsing
- DNS response codes

Example:

```text
BLACKTERM // NETSTACK DNS

interface: eno1
local IPv4: 192.168.50.62
DNS server: 8.8.8.8
hostname: example.com
route: via 192.168.50.1

ARP  who-has 192.168.50.1
ARP  192.168.50.1 is-at C8:7F:54:C1:A1:20

DNS  query A example.com -> 8.8.8.8:53
DNS  response code=NOERROR time=70.77 ms

A    example.com    104.20.23.154
A    example.com    172.66.147.243
```

## TCP

TCP is one of the largest components of NETSTACK.

The project implements TCP packet processing separately from connection-state management.

### TCP Packet Layer

The TCP packet layer provides:

- SYN construction
- header serialization
- parsing
- flag decoding
- IPv4 pseudo-header checksum generation
- checksum validation
- corruption detection
- malformed segment rejection

### TCP Connection Engine

Connection behavior is managed through a reusable TCP connection abstraction.

It tracks:

```text
send_next
send_unacknowledged
receive_next
connection state
retransmission state
retransmission timeout
retry count
```

Implemented state behavior includes:

```text
CLOSED
   │
   │ SYN
   ▼
SYN-SENT
   │
   │ SYN-ACK
   ▼
ESTABLISHED
   │
   │ FIN
   ▼
CLOSE-WAIT / FIN states
   │
   ▼
LAST-ACK
```

The connection engine also provides retransmission timers and exponential backoff.

---

## Live TCP Handshake

NETSTACK can establish a TCP connection by constructing every packet itself.

Example:

```text
BLACKTERM // NETSTACK TCP

interface: eno1
local IPv4: 192.168.50.62
source port: 40000
target: 1.1.1.1:80
route: via 192.168.50.1

ARP  who-has 192.168.50.1
ARP  192.168.50.1 is-at C8:7F:54:C1:A1:20

TCP  SYN
TCP  SYN-ACK
TCP  ACK

TCP STATE: ESTABLISHED
```

At this point, the connection was created through the BLACKTERM TCP implementation rather than a normal userspace TCP socket.

---

## HTTP

HTTP/1.1 support sits on top of the custom TCP connection engine.

Current HTTP features include:

- GET request construction
- Host headers
- response parsing
- status parsing
- header/body separation
- `Transfer-Encoding: chunked` detection
- chunked body decoding
- chunk extension handling

Example:

```text
BLACKTERM // NETSTACK HTTP

interface: eno1
local IPv4: 192.168.50.62
target: 104.20.23.154:80
host: example.com
path: /
route: via 192.168.50.1

ARP  who-has 192.168.50.1
ARP  192.168.50.1 is-at C8:7F:54:C1:A1:20

TCP  SYN-SENT
TCP  SYN-ACK
TCP  STATE        ESTABLISHED

HTTP GET /

TCP  SEND
TCP  DATA
TCP  DATA
TCP  FIN RECEIVED

HTTP RESPONSE
status: 200 OK

--- BODY (chunked decoded) ---

<!doctype html>
<html>
...
</html>
```

The complete path is:

```text
HTTP request
     ↓
TCP segment
     ↓
IPv4 packet
     ↓
Ethernet frame
     ↓
AF_PACKET
     ↓
physical network
     ↓
remote server
```

The response travels back through those layers in reverse.


## Running NETSTACK

Raw Ethernet access requires `CAP_NET_RAW`.

For example:

```bash
sudo setcap cap_net_raw+ep ./build/netstack_ping
sudo setcap cap_net_raw+ep ./build/netstack_dns
sudo setcap cap_net_raw+ep ./build/netstack_tcp
sudo setcap cap_net_raw+ep ./build/netstack_http
```

Verify:

```bash
getcap ./build/netstack_http
```

Expected:

```text
./build/netstack_http cap_net_raw=ep
```

Capabilities may need to be reapplied after rebuilding an executable.

## Important Linux TCP Testing Note

Because NETSTACK constructs TCP connections independently of the Linux kernel TCP stack, Linux may see incoming TCP traffic for a connection it does not recognize.

During controlled development testing, the kernel-generated RST for the dedicated test source port can interfere with the userspace connection.

A temporary nftables rule can be used for the NETSTACK HTTP test port:

```bash
sudo nft add table inet blackterm_http

sudo nft 'add chain inet blackterm_http output { type filter hook output priority -300; policy accept; }'

sudo nft add rule inet blackterm_http output tcp sport 40001 tcp flags rst drop
```

Inspect:

```bash
sudo nft list table inet blackterm_http
```

Remove it after testing:

```bash
sudo nft delete table inet blackterm_http
```

Do not leave development firewall rules behind unnecessarily.

## What NETSTACK Does Not Use

For the implemented raw network flows, the goal is to avoid handing transport behavior to conventional application networking APIs.

The project builds the relevant protocol structures itself instead of simply doing:

```c
socket(AF_INET, SOCK_STREAM, 0);
connect(...);
send(...);
recv(...);
```

Raw Linux packet access is used to move Ethernet frames between NETSTACK and the network interface.

That distinction is the point of the project.

## Testing Philosophy

Every protocol is tested independently before being integrated with the next layer.

For example:

```text
Ethernet
   ↓
ARP
   ↓
Ethernet + ARP

IPv4
   ↓
Ethernet + IPv4

ICMP
   ↓
Ethernet + IPv4 + ICMP

UDP
   ↓
DNS

TCP
   ↓
TCP connection engine
   ↓
HTTP
```

This keeps protocol bugs isolated and makes cross-layer behavior easier to validate.

## Why Build This?

Most networking software starts at sockets.

BLACKTERM NETSTACK intentionally starts lower.

Building the stack from Ethernet upward makes concepts such as:

```text
MAC resolution
routing
checksums
sequence numbers
acknowledgments
retransmissions
connection states
protocol encapsulation
wire formats
```

visible instead of hiding them behind an operating-system networking API.

The goal is not to replace the Linux networking stack.

The goal is to understand what that stack normally does for an application by implementing those mechanisms directly.

```text
Don't just send the packet.

Understand every byte in it.
```

BLACKTERM NETSTACK is built layer by layer, with each protocol tested independently before being connected to the next.

Ethernet became ARP.

ARP became IPv4.

IPv4 became ICMP and UDP.

UDP became DNS.

IPv4 became TCP.

TCP became a connection engine.

And now that connection engine can retrieve a real webpage.
